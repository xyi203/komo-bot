## 0. 结论

本文是一路讨论叠加写成的，**以本节和 §4.11–§4.14 为准**；§4.6–§4.8 是推导过程，与本节冲突处以本节为准。

对面的人感觉到的是**一个 Agent**（§4.12）。内部是 Router - Worker：

- **Router 是一次结构化判断，不是会话**（§4.11）。每条没有直通去处的消息触发一次模型调用，只填固定格式的去向：
  `new` / `continue` / `stop` / `list`（群里另有 `ignore`）。没有工具、没有历史，可单独配模型。分发本身是引擎里的一种任务，重启可恢复（§4.14 F2）。
- **Worker 是任务会话**，动手和回答都在这里，工具是六个基础工具加 `task`、`monitor`、MCP 与 `komo`（§4.4）。结果由程序原文投到渠道。
- **Thread 是把相关东西关联起来的键**（§4.7）：话题或目标。关联可多对多，对话位置的路由归属唯一（§4.14 F5）。
- **不新建"任务"表。** 任务就是现有的任务会话加一个面向人的投影与清单（§3）。不再有人直接开的会话：任务只来自 Router、定时任务和群消息。
- **目标不并进任务**；任务带上目标的键就是归属。领域并进约定，Memos 移出核心概念（§5.4）。
- **人只需要把服务启动起来**：去掉 TUI，命令只留启动，其余进网页；Agent 用的命令由在 Gateway 里执行的 `komo` 工具取代（§4.4、§5）。
- **删会话树的用户入口**（导航与编辑重发、标签、分支摘要、`/fork`、`/clone`）；存储层的 fork 不动。
- **群聊分两条路**（§4.13）：@机器人 以机器人身份直接回；@操作者本人 起草后由操作者批"发不发"，以操作者身份发出（从 Cabinet 并入）。
- **模型调用更容错**（§4.10）：截断后重发、参数先修复、按 schema 宽松转换。

## 1. 问题

会话现在同时承担两件事：技术上的上下文管理，和给用户看的"我手上有哪些事"。后一件它做不好：

| 用户想知道的 | 现在要去哪看 |
|---|---|
| 手上有哪些事在跑 | 侧栏会话树里展开主会话下的子任务；或 `komo session list` 里找标着"任务"的行 |
| 哪件事在等我 | 待处理页（介入）；任务"受阻"只写在交回 home 的那条消息标题里 |
| 这件事做到哪了 | 问 home（它调 `task(task_id)`），或点进任务会话自己读 |
| 上周那件事的结论 | `komo session search`，或翻 home 的历史 |

同时，界面与命令里围绕"会话"长出了不少东西：侧栏三种分组、两种排序、三种筛选、分页；会话树的导航、标签、分支摘要、
分叉与复制；`komo session list/search/export/delete/purge`。这些大多是在帮用户管理会话，而不是管理事情。

home 这边还有一个已知问题（`roadmap-muse.md` S）：home 自己动手还是派任务由模型按工具说明判断，文章的消融实验里这种
形状在中性提示下 5 次一次都没委派。home 自己做的事不会出现在任何任务清单里——任务清单要可信，就得先让"事"都变成任务。

## 2. 目标形态

```text
用户 ──▶ 主对话（home：对话、记忆、事项、派任务、转告结论）
            │ task(...)
            ▼
          任务 #1lxxbx「标题」   进行中 · 3 轮 · 2 分
          任务 #9fk2ma「标题」   等你：受阻，原因……
          任务 #c07pqd「标题」   已交回 · 完成
            │ 点进去
            ▼
          执行记录（就是任务会话的对话，可直接插话、接管）
```

- **主对话只有一条。** 微信、Telegram 私聊、TUI 的 `komo home`、网页首页都是它（§11.2 现状）。
- **任务清单按状态分组**，不按会话树、工作目录或时间。状态全部从已有记录读出，见 §3.2。
- **会话还在，只是不当入口。** 点任务进去看到的就是它的会话；排查用的 `komo session …`、`komo run inspect` 照旧。

## 3. 对象

### 3.1 任务是什么

| 来源 | 现在 | 之后 |
|---|---|---|
| home 调 `task` 派出 | `kind = task`，有 `komo.task`，结果交回 home | **任务**（有派出方） |
| 用户直接新建（TUI `komo`、网页"新对话"） | `kind = normal` | 入口去掉（2026-11-11：不再有直接开的会话）；存量的仍按任务显示 |
| 飞书群 / 话题、Telegram 群 | `kind = normal`，按 peer 路由 | **任务**（绑定一个话题；对应文章的 Thread） |
| Cron 触发 | `kind = cron` | **任务**（不经过 Router，§4.13；运行期间出现在清单里） |
| 主会话 | `kind = main` | 主对话 |

存储不改：`SessionKind` 四个值照旧，"任务"是 `task` 与 `normal` 两种会话在协议层的统一叫法。没有派出方的任务没有
`komo.task`，也就没有状态行、自动续跑与交回（`background-tasks.md` §2c 只对派出的任务生效）——这一点保持现状。

### 3.2 状态（读出来的，不落库）

| 给用户看的 | 判据（都已存在） |
|---|---|
| 进行中 | `komo.live.run` 在；带已跑时长、工具轮数、挂着的监听数 |
| 等你 | 有未答的介入或 confirm（§7.5、`confirm.md`）；或最近一次交回 `status = blocked` |
| 已交回 | `komo.task.lastRun` 有终态：完成 / 没说做完 / 没有完成（失败、取消、预算） |
| 空闲 | 没有派出方的任务，当前没有 Run |
| 已归档 | 会话 `closing` / `deleted`（§8.10） |

"等你"里的 `blocked` 目前只在交回的 `task.result` entry 的 `data.status` 里；`komo.task.lastRun` 只有 `state` / `ended_at` /
`final_message` / `reason`（`orchestration/mod.rs` 的 `LastRun`）。要在收尾提交里把 `status` 与 `rounds` 补进 `lastRun`
（附加字段，旧 document 读出为空，按"没说做完"显示）。

### 3.3 接口

- `GET /v1/tasks`（新，只读投影）：短号、标题、状态（§3.2）、派出方、开始与结束时刻、轮数、挂着的监听、归属的事项。
  实现上是 `GET /v1/sessions` 按 `kind` 过滤再补 `komo.task` 与 live 的几格；单独一条路由是为了让客户端不必知道会话的
  内部字段。分页沿用会话列表的 `limit` / `cursor`。
- ~~`komo task list [--all]`、`komo task show #短号`~~（不做：命令只留启动服务，§5.3；Worker 用 `komo` 工具的 `task.list`）。看门狗的巡检提示（`roadmap-muse.md` S4）从
  `komo session list` 换成它，不用再靠"标着任务、运行列还在执行中"去认。
- 不加 `komo task cancel` 之外的写命令；取消见 §4.3。

### 3.4 与目标的关系

目标回答"在做什么、答应了什么"（`goals.md` §1），没有对话、可以很久不动；任务是一次执行，有对话、会结束。
"这周把 owl 的发布观察做完"是目标，它下面可能先后派出三个任务。所以不合并。

归属不单设参数：任务带上目标的键就是归属（§4.7），目标详情页列出带该键的任务。放在最后一个阶段（T4）。领域并进约定（§5.4）。

### 4.5 Router 只分发：操作者的决定（2026-11-11）

| # | 事 | 决定 | 落到方案里 |
|---|---|---|---|
| R1 | Router 自己答不答问题 | **不答，只分发** | Router 自己只说三种话：派出的回执、关于任务的话（哪个任务、到哪了、要不要停）、听不明白时问一句。其余一律派给 Worker，包括"查一下""这是什么"这类原来它会直接答的 |
| R2 | Router 挂不挂 `monitor` | **不挂** | 监听脚本是 `bash -c`，留着就等于留了 `bash`。要盯的事由任务挂（10-31 的 S2 已支持） |
| R3 | Router 的工具 | **按理说不需要工具** | 只留分发本身要用的：`task`（派、追问、查进度、取消）。`read`、`rg`、`codemode`、MCP 都不给。`komo` 工具留不留见下面"待确认" |
| R4 | 任务结果怎么到你 | **通过渠道通知** | 见下面"待确认"：是程序把任务的回复原文投到渠道，还是仍由 Router 转述一遍 |
| R5 | 怎么接着跟一个任务说话 | 照文章（订阅与直通） | 见 §4.6 |
| R6 | 飞书怎么算 | **主线消息先进 Router**（2026-11-11 定，先前是"还没想好"） | Router 决定是新任务还是接着已有任务；话题里的后续消息直通任务（§4.6、§4.7） |
| R7 | Router 的模型 | **单独配置** | `[agents.<id>]` 加一个可选键 `router_model`（填 `[model.<alias>]` 的 alias）；不写就用 `model`。只这一个键，不恢复旧的 `[home]` 表。文章的经验是 Router 用较轻的模型就够，Worker 用最强的 |

后续决定（均在 2026-11-11）：R1 的"派出的回执"取消（§4.12 U1）；R3 定为 Router 没有工具（§4.11）；R4 定为程序原文直投、不抄给
Router（§4.11、§4.9 B2）；R6 定为飞书主线消息先进 Router。原先的"待确认 1、待确认 2"与默认值随之作废，正文已删。

### 4.6 追问与入口：文章的做法与 komo 的对应（R5、R6）

文章 §3.2：同一个 IM 话题、同一个 PR 下的连续事件是一条 **Thread**。Router 根据 Thread 的第一个事件建 Worker，Worker 随即
**订阅**这条 Thread；之后这条 Thread 里的事件由程序**直通** Worker，不再经过 Router。Router 只管还没人订阅的新事件和跨任务的
协调。输出一侧 Worker 把结论汇报给 Router。

对应到 komo：

| 入口 | 有没有 Thread | 追问怎么走 |
|---|---|---|
| 飞书 | 有：话题。现在已经是一个话题一个会话，话题里的消息由程序直接进那个会话 | 直通，已经是这样 |
| 网页 / 桌面端 | 有：打开某个任务就是在它的对话里 | 直通，已经是这样；在主对话里说的走 Router |
| 微信、Telegram | 没有话题；代码里也没有认"引用回复"的逻辑 | 只能走 Router：它认出是哪个任务，用 `task(task_id)` 转过去（已有，按插话受理）。任务受阻时结果里写着在等什么，你在主对话里答，Router 转回去 |

所以 R5 在 komo 里不用新做订阅机制，缺的只有一处，就是 R6：

- **现状**：飞书私聊的每条主线消息由程序直接开一个新话题和新会话，**不经过 Router**。等于"冷启动也直通"——比文章还省一次
  Router 调用，但 Router 不知道这些任务存在，也没有机会判断"这其实是在接着说上一个任务"。
- **文章的做法**：主线消息先进 Router，Router 决定是新任务（开话题、派 Worker、Worker 订阅该话题）还是转给已有任务；话题里的
  后续消息直通。要改飞书渠道的路由，并让 `task` 派出的任务能绑定一个话题。
- 两种做法下话题里的体验一样，差别只在主线消息：现状快、各管各；文章的做法多一次 Router 调用，换来 Router 掌握全局。
  **操作者 2026-11-11 定：照文章的做法，飞书私聊的主线消息先进 Router。**

### 4.7 Thread：把相关的东西关联起来的键（2026-11-11）

**定义（操作者定）：Thread 就是把一些东西关联起来的东西。** 落到实现上它是一个**键**（一个字符串），不是一个有自己状态和生命周期的
对象：带着同一个键的东西彼此相关。上一版把它说成"任务在渠道上的地址"，窄了——地址只是键的一种用法。

| 谁带着键 | 键从哪来 |
|---|---|
| 进来的消息与事件 | 渠道给的：飞书话题（已有，`ChannelPeer.thread`，写成 `feishu:{chat_id}#{om_root}`）；以后别的来源同理 |
| 任务 | 派出或开出时带上；一个任务可以带几个键（一个话题，加它在处理的那个 MR） |
| 目标 | 目标自己的 id 就是一个键 |

键只做三件事，别的不做：

1. **路由**：进来的东西带着某个键，而这个键有**唯一的路由归属**（见 §4.14 F5）→ 程序直接交给那个任务；没有归属或归属不唯一 → 交给 Router。
2. **找回**：Router 或你提起一件事时，按键找到相关的任务（"这个话题下的任务""为这个目标做的任务"）。
3. **回话的去处**：任务往外说话时，投到它带的键里是对话位置的那一个；没有这样的键就投到主线。

这样三个原本分开的说法收成一个：文章的"订阅"（任务带着话题的键）、D4 的"任务归属到目标"（任务带着目标的键，不再单设 `for`
参数）、上一版的"任务的地址"（键恰好是个对话位置）。不建 Thread 表，键记在任务会话已有的来源与 `komo.task` 里；Thread 没有状态，
"这个 Thread 下有什么"是按键查出来的。

把它说成一条规则，§4.5、§4.6 里分开讨论的三件事就是同一件：

| 规则 | 回答的是 |
|---|---|
| 进来的消息带着 Thread、且这个 Thread 有任务 → 程序直接交给那个任务 | R5 追问 |
| 进来的消息没有 Thread，或 Thread 还没有任务 → 交给 Router；Router 派出任务时，任务得到一个 Thread | R6 飞书主线进 Router |
| 任务往外说的话（结果、受阻时的提问）→ 投到它的 Thread | R4 结果通知 |

各入口的 Thread：

| 入口 | Thread 是什么 | 没有 Thread 的消息 |
|---|---|---|
| 飞书 | 话题。Router 派出任务时，在你那条消息下开话题，任务绑定它 | 私聊主线 → Router |
| 网页 / 桌面端 | 任务自己的对话页 | 主对话 → Router |
| 微信、Telegram | 没有。任务不绑定 Thread，结果带着短号与标题投到主线，追问经 Router 转 | 全部 → Router |

范围与不做的：

- **不建新表，不做订阅管理。** 一个任务可以带几个键，同一个键也可以被几个任务带着，这就是文章的多对多，但不需要订阅 / 退订的
  机制：键跟着任务，任务结束键就不再路由。
- **键的来源先只有两种**：对话渠道的话题、目标。MR、工单、告警要成为键，得先有把它们的事件送进来的来源；现在这些靠任务挂监听，
  事件本来就直接进那个任务，不用键。等真有这样的来源再加，不预先做。
- **用户面前不出现"Thread"这个词**：飞书里叫话题，网页里就是任务的对话。概念清单（§3）不因此变长。
- **代价**：飞书私聊主线从"程序直接开会话"改成先过 Router，每条主线消息多一次 Router 调用（配了 `router_model` 后是较轻的模型）；
  要改飞书渠道的路由，并让 `task` 派出时能开话题、把话题记到任务上。群里 @ 机器人照旧（一个话题一个会话），不经过 Router。

采纳的话：R4 = 原文投到任务的 Thread（没有 Thread 的渠道投到主线），同时抄一份给 Router；R6 = 飞书主线进 Router（已定）。

### 4.8 对照文章的原型与另一份要点（2026-11-11）

操作者另贴了一份对同一篇文章的要点整理（面向"从零做个人助手"）。同时读了本机的原型 `../dsh-superagent-prototype`
（提交 `6337fc8`；`docs/001-domain.md`、`docs/003-execution.md`、`prompts/replies.md`、`prompts/orchestrator.md`、
`src/app/sessions.ts`）。原型自己声明与文章不完全一致。与本方案对照：

| 点 | 原型 / 要点怎么说 | 本方案 | 处理 |
|---|---|---|---|
| Router 不执行要靠架构约束 | 文章实验：单会话加 Subagent 工具，中性提示下 5 次都没委派 | Router 只有 `task`（§4.5） | 一致 |
| Router 的工具 | 原型的主会话并非没有工具：有回复工具（按用途校验：结果 / 提问 / 回答）、派工、带 5 秒限制的 shell | 操作者定"不需要工具" | 更严。因此"对人说话"不能靠 Router 调工具，只能由程序投递，见下一行 |
| 谁对人说话 | 文章：Worker 不直接对人说话。原型是混合的：Worker 在原话题里确认接单（程序代发）；结果和提问由主会话发，Worker 的提问**原样转发**，不改写 | 程序把任务的回复原文投到它的 Thread，同时抄一份给 Router（§4.7） | 与原型"程序代发、原样转发"同向；Router 没有回复工具时这是唯一做法 |
| 直通之后 Router 知不知道 | 话题里的后续消息直通 Worker，主会话收到一条 `follow_up` 通知 | 直通的追问 Router 不知道，只在任务再次交回时看到结果 | 不加通知：Router 不替任务做决定，知道了也无事可做 |
| IM 篇幅 | 单条不超过 100 词，由发送层硬拒，长内容落文档 | komo 已有渠道篇幅的约束（`roadmap-muse.md` S5） | 原文直投之后，说话的是任务而不是主会话，这条约束要跟到任务的最后回复上 |
| "等人"怎么判定 | 原型拒绝从自由文本推断，Worker 用结构化字段提问 | komo 用回复末行"状态：受阻：原因"，带契约时走 JSON | 不改。清单的"等你"读的是交回时解析出的 `status`（§3.2） |
| 任务表、Thread 表 | 要点建议建表；原型的 Ticket 状态独立于 Session，因为一张工单会换执行器、被多个执行器接手 | 任务 = 会话，一对一，不建表（D1）；Thread 记在会话来源上（§4.7） | 不改。komo 的任务不换执行者，原型建表的理由不成立 |
| Thread 的范围 | 同一个 MR、话题、告警都算 | 只算对话渠道；MR、告警由任务挂监听 | 不改（§4.7） |
| 权限 | 要点建议 Worker 默认只读、写操作白名单加确认 | komo 没有 Policy：模型要的就执行，审批 10-11 已删（`komo_bot.md` §7） | 不采纳，与现行规格相反，要改是另一个决定 |
| 提前行动、Watchdog、存算分离 | 要点列为第三期 / 可简化 | Watchdog 已有（S4 看门狗 Cron）；提前行动不在范围；Gateway 可能在远程机器上，`komo` 工具已按此设计（§4.4） | 不改 |

### 4.9 从 OpenClaw 与 Hermes 借鉴的六点（2026-11-11 操作者同意写入）

出处是两家最新文档（OpenClaw `docs/tools/subagents/announce.md`、`thread-bound-sessions.md`、`concepts/decision-models.md`；
Hermes `website/docs/user-guide/features/delegation.md`）。前五点采纳，第六点待定。

| # | 规则 | 出处 | 落到 komo |
|---|---|---|---|
| B1 | **任务必须交回结果或明确的卡点，不许沉默**（只管由人的消息起的轮次，§4.14 F6） | OpenClaw：子任务回 `NO_REPLY` 或空输出不算交付，触发补救；只有父会话可以安静收下 | 任务会话的最后回复是 `NO_REPLY` 或空时，不当作完成：程序追问一次，仍为空就以"无输出"交回并通知操作者。`NO_REPLY` 只留给 Router 收 `task.result` 那一轮。Router 不干活，任务再沉默，这件事就无声消失 |
| B2 | **结果由程序原样交付，不让模型再写一遍** | OpenClaw 明写交付不要求再生成一段通告；Hermes 把结果作为新消息投回 | 即 R4 的"原文直投、抄一份给 Router"（§4.5 待确认 1 的建议项）。两家做法一致，本方案按此定 |
| B3 | **回话的去处在派出时写定** | OpenClaw：派出那一轮记下的来源决定结果投到哪个聊天和话题，之后不变 | 任务的 Thread 键（§4.7）在派出时写进任务，完成时照它投递，不在完成时再推断；派出时没有对话位置的键就投主线 |
| B4 | **按"没有进展"判卡死，不按总时长** | Hermes：去掉总时长上限（300 秒、600 秒曾误杀正常任务），改为轮次之间 450 秒、工具内 1200 秒无活动才中断，到约 80% 时先提醒收尾 | Router 看不到任务内部，卡死要由程序发现：任务在阈值内没有新的模型调用、工具开始或进度提交，先给它插一条收尾提醒，再无进展就停掉并按 B5 交回。不设总时长。阈值先照 Hermes，做成配置 |
| B5 | **被停掉的任务也交回已有的部分** | Hermes：停止后仍作为一次完成返回，状态 `interrupted`，带部分输出 | `task` 的 `stop`（§4.3）与 B4 的中断都交回一条 `task.result`，状态标明是被停的，正文是任务已有的最后产出 |
| B6 | **分发用单独的模型角色，返回固定结构**（操作者 2026-11-11 定：采纳，见 §4.11） | OpenClaw 分主模型、`utilityModel`、`decisionModel`，后者做分类与路由，返回带类型的答案 | R7 的 `router_model` 已覆盖"单独的模型"。更进一步是把分发做成一次结构化判断（新任务，还是接着某个任务）而不是一轮对话；komo 的模型层有 typesafe judge，能否直接用未核对（§8） |

不照搬的三样：Hermes 的看板（独立任务库加十四个 `kanban_*` 工具，为多个具名 Agent 协作而设；本方案不建任务表）；OpenClaw 的进度卡
（只给操作者正在对话的会话，Router 不干活，无内容可写）；OpenClaw 的嵌套编排（深度上限、逐层回报、让出后接续；komo 的任务不再派任务）。

### 4.10 从 pi-rust 借鉴的三点：模型调用的容错（2026-11-11 操作者同意写入）

出处是 `bigfish1913/pi-rust`（pi 的 Rust 移植，0.22.0）。三点都在模型调用与工具调用这一层，与 Router-Worker 的关系是：任务没人盯着、
Router 与 Worker 可以用较轻的模型（R7），一次可恢复的小错不该让任务失败或白跑一轮。三点互不依赖。

| # | 规则 | pi-rust 的做法 | komo 现在 | 改法 |
|---|---|---|---|---|
| P1 | **回复被截断时不让整轮失败** | 带工具调用的回复因输出上限被截断：工具不执行，每个调用回一条"超出输出上限"的错误结果，循环继续，模型自己重发（`rpi-agent/tests/truncate_fail.rs`） | 同样不执行，但把这一轮记成 `model_error`，任务失败（`komo-runtime/src/durable/harness/generation.rs` 的 `StopReason::Length` 分支，`fail_with_message`） | 截断且带工具调用时，保留这条 assistant entry，给每个调用落一条错误结果 entry，进入下一轮请求；不带工具调用的截断保持现状。连续截断要有上限（建议 2 次），到上限再按现在的方式失败，免得死循环 |
| P2 | **工具参数的 JSON 先修再解析** | 严格解析失败后，先转义裸控制字符与非法反斜杠再试，仍失败就补上没闭合的字符串、对象、数组（`rpi-ai/src/json_parse.rs`） | 解析失败直接当成空对象（`komo-llm/src/model_stream.rs` 的 `lenient_arguments`），工具随后报缺参数，模型再来一轮 | `lenient_arguments` 改成三层：严格解析 → 修复后解析 → 补闭合后解析。全失败时：流正常结束的按"没收齐"整轮重试（实现时定，不给空对象，免得工具带着空参数执行）；流中途的部分回复才给空对象。只在流正常结束时用补闭合这一层；截断的回复走 P1，不执行半截参数 |
| P3 | **参数按 schema 做宽松转换再校验** | 字符串形式的数字与布尔转成对应类型，可选字段的 `null` 当作没传，然后再校验（`rpi-ai/src/schema.rs`） | 没有这一层 | 在工具的 `prepare` 之前加一步，按该工具的 JSON Schema 转换：字符串 → 数字/整数/布尔，可选字段的 `null` 去掉。只做这几种无歧义的转换，其余原样交给 `prepare` 报错 |

约束：三点都不改 entry 不可变、一次提交一个事务的规则（P1 多落的是错误结果 entry，走现有的工具结果提交路径）；转换与修复发生在
`ExecutionPlan` 写进 `execute` 检查点之前，所以回放看到的是转换后的参数，重启前后一致。

没借鉴的：崩溃后保住已生成的半条回复、工具结束后丢弃迟到的进度更新、嵌套工具执行（komo 已有对应机制）；插件 ABI、TUI、远程模式
（方向无关或正在删）。严格模式的工具 schema 未核对 komo 现状，见 §8。

### 4.11 Router 是一次结构化判断，不是一个会话（2026-11-11 操作者定）

操作者定：B6 采纳。Router 不再是一个带历史、带工具的会话，而是每条进来的消息触发的一次模型调用，只填一个固定格式的答案，
由程序照答案去做。**本节取代 §4.2 的能力面与提示、§4.3 的"查任务清单"、§4.5 的待确认 1 和待确认 2；与本节冲突的旧说法以本节为准。**

**什么时候调用。** 进来的消息按 Thread 键先路由（§4.7）：有活着的任务带这个键，直接交给它，不调用 Router。其余的才调用。

**输入**（程序拼好，没有对话历史、没有工具）：

- 这条消息的原文；
- 进行中与等你的任务清单：任务号、标题、状态、最后一次往外说的话的开头；
- 主线上最近几条消息（微信、Telegram 没有话题，"接着说"只能靠这个判断；条数做成配置，先取 6）。
- 最近结束的几个任务：任务号、标题、结果的开头（见下面决定 2）。

**输出**（固定结构，四选一）：

| 去向 | 带什么 | 程序做什么 |
|---|---|---|
| `new` | 任务说明（把用户的要求写完整）、标题 | 派一个 Worker，带上这条消息的 Thread 键；用户原话与主线最近几条消息随任务一起交给它（U4）；不发回执（U1） |
| `continue` | 任务号 | 把这条消息原文交给那个任务；任务已结束就把它接着做起来 |
| `stop` | 任务号 | 叫停那个任务，按 B5 交回已有的部分 |
| `list` | — | 程序直接把任务清单发回去，不经模型 |

判断失败（模型报错、答案不合格式、任务号不存在）一律按 `new` 处理：宁可多开一个任务，不丢消息。

**随之而来的改变：**

| 原先的写法 | 现在 |
|---|---|
| Router 的工具是 `task` + `komo`（§4.2、待确认 2） | Router 没有工具，与 R3"按理说不需要工具"一致。`task`、`komo` 只给 Worker |
| 记目标、记约定由 Router 用 `komo` 做 | 由 Worker 做。现行规则是任务会话不能改承诺类内容（要有用户原话）；改成：由用户消息派出的任务带着用户原话，允许改；任务再派出的任务、Cron 仍然不允许 |
| 结果原文直投，同时抄一份给 Router（待确认 1、B2） | 只直投。Router 没有历史，不需要抄；它下次判断时从任务清单里看到这个任务的状态 |
| Router 收到结果后回 `NO_REPLY`（B1 的例外） | 没有这一轮了。B1 只管"由人的消息起的那一轮"；只由监听事件起的轮次照旧可以回 `NO_REPLY` 静默收尾（§4.14 F6） |
| "手上有哪些事"用 `komo` 的 `task.list` 查（§4.3、D6） | Router 判为 `list`，程序直接出清单。`task.list` 仍留给 Worker |
| 叫停任务靠 `task` 的 `stop`（§4.3） | Router 判为 `stop`，程序去停。`task` 的 `stop` 不再需要 |
| 从主会话 fork 的任务改用 Worker 能力面（§4.2） | 没有可 fork 的主会话上下文，任务一律 fresh。提示缓存失效的问题随之消失 |
| `router_model`（R7） | 保留，就是这次判断用的模型 |
| 系统提示给主会话加 Router 说明、带记忆与目标注入（§4.5 默认值） | Router 的提示只有分发规则和上面的输入，不带记忆与目标。记忆与目标注入 Worker |

**"主对话"还剩什么。** 界面上仍有一条主线：你发的消息、任务往主线投的结果，按时间排。它是显示用的时间线，不再是哪个模型的上下文。

**三件事的决定（操作者 2026-11-11：按建议来）：**

1. **闲聊和一句话的问题也开任务：接受，Router 不直接回。** 允许回一句，"什么算一句话能答的"就得靠模型自己把握，会慢慢越界去答本该
   派出去的事，正是 R1 要防的。答完即结束的任务不进清单（清单默认只显示进行中与等你的），代价只是每条消息多起一个任务会话。
   跑起来后如果闲聊回得慢，再单独处理。
2. **Router 不带历史，输入里补一项"最近结束的任务"。** 任务清单除进行中与等你的之外，再带最近结束的几个（任务号、标题、结果的开头；
   个数做成配置，先取 5）。"还是按上次那样""刚才那个再改一下"多半指刚结束的任务。Router 判成 `continue` 并指向已结束的任务时，
   程序往那个任务的 conversation 提交这条消息，它带着自己的历史接着做——这是现有的"接着做"路径（`background-tasks.md` §2，
   已核对：任务的 conversation 结束后一直在），不是新机制。仍判不出的当新任务，由 Worker 去查记忆与历史。
3. **主线消息沿用主会话的存储，只是不再跑模型。** 已核对（`komo-runtime/src/durable/harness/inbox.rs` 头部的受理表）：只用于展示的
   write（不带 `model` / `head` / `edits`）受理后直接追加 entry，忙闲都立刻落，不建 run。用户发到主线的消息、任务投到主线的结果都按
   这种 write 落进 `kind = main` 的 conversation。好处：旧数据不用迁移；不多一处存储。**"读主对话的接口不用改"撤回**（审查 F3，已核对）：事件投影从 `entry.model` 取正文
   （`legacy_events.rs`），展示 write 没有 `model`，投不出消息；客户端遇到不属于任何 Run 的 assistant 消息会丢掉
   （`apps/client/.../conversation/model.ts`）。要补两样：主线消息（用户发的、任务投回的）各自的事件映射；客户端一条不依赖 Run 的渲染路径。
   主会话不再有 run，它的压缩、提示缓存、`NO_REPLY` 都随之用不上。

### 4.12 对外是一个 Agent（2026-11-11 操作者定）

操作者定：尽量让对面的人感觉是在和一个 Agent 聊，不要感觉到有 Router 在派任务。Router、Worker、任务号都是内部的事。
**与本节冲突的旧说法以本节为准**，主要是 §4.5 R1 的"派出的回执"和 §4.8 里"Worker 在原话题确认接单"。

| # | 规则 | 说明 |
|---|---|---|
| U1 | **没有派出回执** | 不发"已为你创建任务""已派给……"。消息进来后只显示"正在输入"（渠道支持的话），第一条看得见的话就是 Worker 的回复本身 |
| U2 | **Worker 用同一个身份说话** | 所有 Worker 用同一个 Agent 的名字、人设与语气；回复里不出现"任务""Worker""Router""子代理"这些词，不自称"我是负责……的任务" |
| U3 | **回复原样发，不加包装** | 不加"任务结果：""T12 完成："这类前缀。任务回复末行的状态行（`状态：完成` / `状态：受阻：原因`，`background-tasks.md` §2c）是给程序看的，投递前去掉；带结果契约的 JSON 也不外发 |
| U4 | **新任务接得上前面的话** | Worker 从空白开始会显得"失忆"。新任务起步时带上主线最近几条消息（与 Router 的输入用同一份）以及记忆与目标注入，让它像在接着聊 |
| U5 | **对人不出现任务号** | 任务号只在程序与 Router 之间用。对人用标题或"刚才那件事"指代；`list` 的清单用自然的说法列出正在做的事和等你回话的事，不带编号 |
| U6 | **提问、受阻、停下，都是普通的话** | Worker 做不下去要问你，就直接问（原样发，§4.8）；被叫停时回一句"好，先停了，做到了……"；卡死或无输出（B1、B4）由程序发一句自然的话，如"这件事我没做成，要不要再试一次"，不发状态码 |
| U7 | **回到你说话的地方** | 飞书回在那条消息的话题里；没有话题的渠道回在主线。同时有几件事在做时，能引用原消息的渠道就引用，让你知道这句是在答哪一条（各渠道能否发引用回复未核对，§8） |
| U8 | **界面上主对话是主角** | 网页与桌面端以一条对话为主，任务清单退到侧边，名字用"正在做的事"一类的说法，不用"任务 / Router / Worker" |

代价：没有回执之后，一件要做很久的事在出结果之前是安静的。缓解只有两条，都不暴露派发：Worker 自己在开头说一句打算怎么做
（提示里要求，耗时的事先回一句再动手）；你问"在做什么"时由 `list` 回答。

### 4.13 定时任务与群聊的会话（2026-11-11）

**定时任务：不经过 Router，直接算一个任务（操作者已定）。** 到点由程序开，自己把事做完；结果按现有的 `notify`
（`always` / `on_error` / `never`）投出去，`cron_watch` 不变。运行期间出现在"正在做的事"里。它仍然不能再派任务。

**群聊：经过 Router（操作者已定），可能要审批，操作者也可能自己直接回。** 现状（已核对，`komo_bot.md` §11.3）：飞书群里 @机器人 的
消息以话题回复，一个话题一个会话，话题里的后续消息直接进那个会话；没 @ 的消息不触发。改成：

- **群里的第一条（@机器人、还没有任务的话题）先进 Router**；话题里已有活着的任务时照 Thread 键直通，不再判断（§4.7）。
- **群消息的判断只看这个群**。输入是这条消息、**这个群里**进行中与最近结束的任务、这个话题或群里最近几条消息；不带操作者私聊的
  任务清单与主线消息。原因：komo 可以配成"同一企业的人都算操作者"（`allow_tenant`），带上私聊的清单，同事在群里说一句"先别做了"
  或"你手上有哪些事"就能停掉或列出操作者私聊里的任务。
- **去向比私聊多一种、少一种**：`new`、`continue`、`stop`（只能指这个群里的任务）、`ignore`（不该由 Agent 接的，比如明显是在问操作者
  本人）；没有 `list`。判断失败在群里按 `ignore` 处理而不是 `new`——私聊里宁可多开任务，群里宁可不说话。
- **审批：批"回复发不发"（操作者 2026-11-11 定，与 Cabinet 现在的做法一致；只用于 @操作者本人 的消息，见下表）。** Worker 照常把事做完，
  回复先不发到群里，作为草稿发到操作者的私聊；批了才投到群里的那个话题。操作者本人在群里 @ 的不用审批。**草稿只投给操作者本人的私聊，绝不投来源会话**：
  现有的 `deliver_attention`（`interventions/mod.rs`）是"来源对端 + home chat"双投，直接复用会把没批的正文和备注发回来源群（审查 F1）。
  只复用介入的答复幂等，投递单写一条只到操作者的路；不新做审批表。细节照 Cabinet（`server/drafts/`，已读代码）：
  - **三个动作**：发 / 改了再发 / 不发。草稿在卡片里可以直接改字再发，处理完卡片原地更新成结果。
  - **给操作者的备注不外发**：Worker 把查证依据、拿不准的地方写在备注里，只有草稿正文会进群。
  - **并发只生效一次**：卡片和网页同时点，只有一个生效（Cabinet 用状态的原子切换；komo 用介入答复的幂等）。
  - **涉及要操作者拍板的事**（审批、合并、发布、排期、承诺时间）：草稿只写中性回应，不替操作者决定，在备注里提醒。
- **草稿作废的四种情况**（照 Cabinet 的 `replied.ts`）：
  - 操作者本人已经回了。群里要有明确指向才算：回复了那条消息、@了对方、或在同一个话题里发了话。
  - 操作者在那条消息上回了表情。表情不是消息，收不到事件，要逐条查。
  - 对方又接着发了：这份草稿作废，几条合在一起由后面那条重新起草。
  - 起草之前、推草稿之前各再查一次上面三条，已经不需要就不起草、不推。
  任务还在做的时候遇到这些情况，同样停掉（按 B5 留着已有的部分，不外发）。
- **按 @ 的是谁分两条路（操作者 2026-11-11 定）：**

  | 消息 | 以谁的身份发 | 审批 |
  |---|---|---|
  | @机器人 | 机器人 | 不审批，Worker 的回复直接发到那个话题 |
  | @操作者本人 | 操作者本人 | 批"发不发"，上面的草稿规则与作废规则都只用在这条路上 |

  所以上面的"审批"与"草稿作废"只适用于 @操作者本人 的消息；@机器人 的消息照 §4.12 直接回。Router 的 `ignore` 两条路都有。
  **@操作者本人 这条路并进 komo（操作者 2026-11-11 定）。** 现在由 Cabinet 在做，komo 要补的能力照 Cabinet 的做法（README 与
  `server/drafts/`、`server/lark/` 已读）：
  - **用操作者个人的飞书身份收发**。飞书渠道现在只有机器人身份（App ID / Secret）。要加用户身份：OAuth 授权码流程拿到
    refresh_token，到期前自动刷新，凭证按 komo 的规则放 `.env` 一侧而不是库里；授权入口放网页。
  - **收**：个人身份收不到事件推送，Cabinet 是轮询操作者的私聊与群里 @操作者 的消息。komo 的渠道插件要加一条轮询的入站路。
  - **发**：以操作者身份发出只有一个入口，只由操作者的"发"触发（卡片、私聊里引用卡片回一句、网页，三处等价）；这个入口
    不做成工具，Worker 调不到。
  - **草稿卡片**：由机器人私聊发给操作者，可直接改字再发，处理完原地更新；komo 现有的飞书卡片只有"处理中 → 结果"一张，要加这张。
  - **Worker 在这条路上用完整的工具，不做只读**（2026-11-11 修正；上一版写的"只读、`bash` 受限"撤回）。两个原因：代码评审要拉代码、
    跑单测，只读做不了；komo 没有命令守卫，也不打算有（`AGENTS.md`："bash cannot be stopped"，没有 Policy），"受限的 bash"在 komo 里
    本来就不成立。工具与普通任务相同，所以缓存也不用分开算。别人发来的消息是不可信的输入，靠下面三条挡，而不是靠削工具：
    - **回复本身要批**：发到群里的话只有草稿这一条路。
    - **其余对外动作走现有的确认**：这类任务不是操作者发起的，调用标了 `outward` 的工具时停在 `confirm` 等操作者批（`docs/confirm.md`，
      现有机制；§4.11 放开的只是"由操作者的消息派出的任务"）。
    - **在单独的目录里干活**：给这类任务一个独立的工作目录（拉下来的代码、跑测试的产物都在里面），不落在操作者平时的工作目录。
      这只是隔离误伤，不是安全边界。
  - **凭证不是硬边界，如实写**：上一条"Worker 拿不到个人身份的凭证"在有 `bash` 的前提下做不到绝对——凭证落在本机，`bash` 读得到，
    这与现在机器人凭证的处境相同，只是以操作者身份发消息的后果更重。能做的是：凭证不进任何提示与工具结果，发送入口不做成工具；
    真要硬隔离只能靠执行环境（另一个系统用户或容器），不在本方案范围，记为已知风险。
  - **口吻**：草稿用操作者的第一人称，简短；不提自己是 AI。这是 §4.12 之外的另一套说话规则，单独一段提示（Cabinet 的 `config/draft.md`）。
  - **不在这次范围里的 Cabinet 功能**：飞书项目评论、告警批处理、MR 预审、看板的其余页面。要不要一并迁，另议。
- **群里开出的任务不带操作者的个人记忆与目标**（未核对现在的记忆作用域怎么定，§8）。

### 4.14 审查后的修正（2026-11-11，六条均已对照代码核实）

| # | 问题 | 修正 |
|---|---|---|
| F1 | 草稿复用介入的双投，会在批准前把正文和备注发回来源群 | 草稿只投操作者私聊，只复用答复幂等（已改在 §4.13） |
| F2 | 主线消息落盘后、派出前重启，消息显示了却没有工作可恢复；重试又可能重复建任务 | 见下面"分发的持久协议" |
| F3 | 展示 write 没有 `model`，现有投影投不出消息；客户端丢弃没有 Run 的 assistant 消息 | 补主线消息的事件映射与不依赖 Run 的渲染路径（已改在 §4.11 决定 3） |
| F4 | 叫停只取消当前执行，任务挂着的监听下一次事件仍会起 Run，任务停后复活 | 见下面"停下的含义" |
| F5 | 同一个键允许多个任务带着，路由却要交给"那个任务" | 见下面"关联多对多，路由唯一" |
| F6 | 任务里一律禁 `NO_REPLY`，会让只由监听事件起的轮次（现在靠它静默）触发补救或"没做成"通知 | 见下面"B1 的适用范围" |

**分发的持久协议（F2）。** 分发本身做成引擎里的一种任务，不是提交之外的一段程序，这样恢复照现有的表走（`running` 回到 `pending`，
从检查点续）：

1. **受理**：主线消息的展示 write 与一个"分发任务"在**同一次提交**里落下。write 的请求键是平台消息键（现有的持久去重：平台重投返回原记录），
   所以一条消息至多一个分发任务。
2. **判断**：分发任务的第一个检查点。调模型、得到去向，把去向写进检查点。判断没有副作用，重启后重做无妨。
3. **执行**：第二个检查点，**一次提交**里同时做两件事——按去向落效果（建任务 / 往目标任务提交输入 / 登记停止 / 落清单消息），
   并把分发任务标成完成。提交给目标任务的输入用 `dispatch:{主线消息的 entry id}` 作请求键，所以即使执行这一步被重放也不会重复。
4. **失败**：判断连续失败到上限按 `new` 执行（§4.11）；执行失败是存储错误，整条线失败，照现有规则。

群消息与 @操作者本人 的消息走同一协议，只是受理落在各自的 conversation 里。

**停下的含义（F4）。** "叫停"不只是 `abort_conversation`，是三件事在一起：

- 撤回排队的输入并 abort 当前执行（现有的 `abort_conversation`）；
- 停掉这个任务名下还活着的监听，登记 `ended{stopped}` 且不交回结束消息（删会话时已有这段逻辑，`sessions/lifecycle.rs` 的
  `stop_monitors`，提出来共用）；
- 把任务标成"已停"：收件箱里排着的、以及在途晚到的监听事件一律丢弃不起 Run（现在 `abort_conversation` 有意保留内部输入，对已停的任务
  要反过来）。只有人的消息经 Router 判成 `continue` 指向它，才清掉这个标记重新做起来。

草稿作废、B4 的卡死中断都用这同一个"停下"。

**关联多对多，路由唯一（F5）。** 键仍然可以被多个任务带着（用于找回与归属），但"对话位置"这种键另有一个**路由归属**，每个位置至多一个任务：

- 归属在派出时写定（B3），给的是这次派出的任务；归属的任务结束或被停，归属清空。
- 进来的消息：位置有归属 → 直通；没有归属，或因并发出现了两个候选 → 交给 Router，把带着这个键的任务都作为候选放进输入，由它判
  `continue` 给谁或 `new`。Router 判 `new` 且原归属已空时，新任务拿到归属。
- 目标这种键没有路由归属，只用于找回与归属。

**B1 的适用范围（F6）。** "不许沉默"只管由人的消息起的那一轮（派出的首轮、`continue` 送进去的消息）。只由监听事件或结束消息起的轮次
（`report.rs` 的 `events_only`）保持现状：回 `NO_REPLY` 就不交回、不通知。否则一个每分钟轮询一次的监听，每次"没变化"都会触发追问或
"没做成"的通知。带混合输入的轮次（既有人的消息又有事件）按人的消息算。

### 4.4 核心工具面怎么分（2026-11-10 操作者问）

现状（`komo_bot.md` §4）：六个基础工具 `read`、`write`、`edit`、`rg`、`bash`、`codemode`，明写"不新增第七个"；`task`、
`monitor`（含 `monitor_stop`）是编排操作，不算新能力；MCP 是操作者接进来的。komo 自己的状态（记忆、事项、定时、找会话）没有
工具，由 `SELF_BLOCK` 教模型在 `bash` 里跑 `komo <子命令>`。所有会话拿到的是同一套。

建议保留这套分法，只做两件事：**按会话的角色给不同的能力面**，以及**把"komo 自己的状态"单独成一层**。

| 层 | 工具 | 任务会话 | 主会话（home） |
|---|---|---|---|
| 做事 | `read`、`rg`、`codemode` | 有 | 不给（§4.5 R1） |
| 做事（有副作用） | `write`、`edit`、`bash` | 有 | 不给（§4.2） |
| 编排 | `task`（加 `stop`，§4.3）、`monitor` | 只有 `monitor` | 只有 `task`（§4.5 R2） |
| 自己的状态 | `komo` 工具（记忆、目标、定时、找会话） | 有 | 待确认（§4.5） |
| 外部 | MCP | 有 | 不给（§4.5 R3） |

几条判断：

- **加不加工具，沿用 §4 已有的那条标准：计划不一样才值得单独成工具。** `rg` 能从 `bash` 里分出来，是因为它的计划是只读、
  可并发、中断后可直接重跑，而 `bash` 是顺序屏障、恢复默认不安全。`komo memory search`、`komo session search` 也是只读查询，
  现在却按 `bash` 的规矩走。这是"自己的状态"值得单独成层的理由，不是"别家都这么做"。
- **只加一个，不加四个；在 Gateway 进程里执行，不经 shell。** 操作者指出 komo 可能在远程机器上（2026-11-10）：命令执行的地方不一定
  有 `komo` 二进制、也不一定连得到 Gateway，所以"一个只能跑 komo 自己的 `bash`"那个初版作废，Hermes 不让 shell 调 `hermes kanban`
  是同一个理由。工具改成直接调 Gateway 里已有的那层：记忆、事项、定时、找会话现在都有 HTTP 路由和带类型的请求
  （`/v1/memories…`、`/v1/matters…`、`/v1/cron…`、`/v1/session-search`；`MemoryAddRequest`、`MatterAddRequest`、
  `MatterActionRequest`、`CreateCronRequest` …），CLI 只是它们的客户端。工具收 `action` 与 `params`，`params` 直接反序列化成
  这些现成的请求类型，调路由背后的同一个处理函数；会话与 Run 的身份取自 `ToolContext`，不再靠 `KOMO_SESSION` / `KOMO_RUN`。
  只读动作声明成可并发、可重跑。
  **操作者 2026-11-10 确认：工具直接调接口背后的同一个处理函数，不另写一套逻辑。**
- **加（2026-11-10 操作者定）。** 所有会话都挂，`SELF_BLOCK` 改成指向这个工具，提示里只有一种说法。Agent 用的那几组 CLI 子命令
  随之可以删掉而不是藏起来（并存一个版本后删），D8 因此真的只剩启动服务。主会话不挂 `bash`（§4.2）。
- **命名：工具叫 `komo`，参数是 `action` 与 `params`。** `action` 用"领域.动作"的写法并列成 enum，模型从 schema 就看得到全部动作：
  `memory.add`、`memory.search`、`memory.forget`、`goal.add`、`goal.next`、`goal.wait`、`goal.resume`、`goal.done`、`goal.link`、
  `cron.list`、`cron.run`、`session.search`、`session.list`（以现有子命令为准，不含 `memory.confirm`——那是用户的动作，
  也不含 Gateway 的重启与停止）。`params` 在 schema 里只是一个对象，各动作的字段写在 `tool://komo/doc`，填错时 `prepare` 的报错列出
  该动作认的字段。写法照 OpenClaw 的 `gateway` 工具（`config.get`、`update.run` …）。没选的名字：`self`、`state`、`manage` 看不出
  管的是什么；`gateway` 在 komo 里指进程；按领域起名就回到四个工具。
- **先例（读本机代码，四家之外没查）。** 没有哪家是"一个工具原样转给自家命令"。最接近的是 OpenClaw 的 `gateway` 工具：以自家组件
  命名，一个工具用 `action`（`config.get`、`config.schema.lookup`、`update.run`、`restart`、`update.cleanup`）管运行时自己，但只管
  配置与维护，记忆、定时、会话各有工具。Hermes 一个领域一个工具，并在提示里明写不要 shell 去调 `hermes kanban`，理由是工具在
  所有终端后端下都能用（它的终端可以在容器或远程机器上，那里没有 `hermes`）。Cabinet 是 `memory`、`lookup`、`schedule` 三个。
  与它们的差别只剩：komo 把几个领域收在一个工具里，各动作的字段不进 schema、放在 `tool://komo/doc`，代价是模型第一次用某个
  动作可能多一次读说明的往返。
- **不加"问用户"的工具。** OpenClaw 有 `ask_user`、Hermes 有 `clarify`，都要人在场。komo 的任务会话中途没人能答
  （`TASK_MODE_BLOCK`），要人决定的事走交回时的"状态：受阻"，在清单里显示为"等你"（§3.2）；主会话本来就在对话里，直接问。
- **不加 `todo` / 计划工具。** `update_plan` 10-16 已退役；任务清单是从会话读出来的投影（§3），不是模型维护的一张表。

|---|---|---|---|
| TUI 斜杠命令（`komo-client/src/tui/command.rs`） | 16 条：`/new` `/cancel` `/status` `/pending` `/answer` `/model` `/effort` `/tree` `/fork` `/clone` `/name` `/label` `/context-edit` `/compact` `/help` `/quit`，外加 `!` 直跑 shell | 只有终端前的操作者 | **全部消失** |
| CLI 子命令（`komo …`，`crates/komo/src/main.rs`） | 顶层 20 个 | 操作者，**以及 Agent 自己**：它在 `bash` 里跑 `komo memory add/search/confirm`、`komo goal …`、`komo area …`、`komo skills …`、`komo mcp reconnect`、`komo cron list`、`komo session list/search`、`komo gateway restart`（系统提示与工具文档里教的） | 只少 `komo home`、`komo resume`；裸 `komo` 要换个含义 |
| 渠道命令（`dispatcher.rs` 的 `parse_command` 与介入答复） | `/pending` `/new` `/cancel` `/status` `/id`、`/answer` `/approve` `/deny` | 飞书 / Telegram / 微信里的操作者 | 不变 |

所以答案是：**斜杠命令能整套去掉，CLI 子命令基本去不掉**——它们是 Agent 的工具面，不是 TUI 的附属。

去掉 TUI 顺带带走的：

- `komo-client/src/tui/` 约 1.39 万行（整个 crate 2.05 万行），含会话树选择器、Markdown 渲染、粘贴、工具视图与约 2000 行测试；
  `ratatui`、`crossterm`、`pulldown-cmark` 三个依赖只有它在用，可从 §13.4 依赖表删掉。`api.rs`、`sse.rs`、`render/`（CLI 的
  输出）留下。
- §5 里标"删"的会话树入口大半随之消失：`navigate`、`label`、`context-edit`、`compact` 四条路由的调用方只有 TUI，网页不调
  （网页调的会话写接口只有新建、`fork`、`name`、`delete`、`purge`）。D5 就只剩网页菜单里的"分叉"一项要决定。
- `resume` 路由（`komo resume` 用）与 `boundary` 路由的 TUI 一侧；`boundary` 渠道的 `/new` 还在用，留着。

代价，要先想清楚的：

- **终端里没有对话入口。** 剩下网页（`komo web`）和渠道。SSH 到一台没有浏览器的机器上时只能走渠道，或把网页经隧道转出来
  （`clients.md` 的远程访问还没做，C3）。
- **首次上手路径变了。** `PRODUCT.md` 原则 2 写的是 init → 配 key → chat；chat 这一步从"终端里直接打字"变成"浏览器里配对
  后打字"。建议裸 `komo` 改成：确保 Gateway 就绪后做 `komo web` 的事（要配对码、开浏览器），`komo web` 留作别名。
- **手动压缩没有入口。** `/compact` 只在 TUI；在线压缩是自动的（§6），网页要不要补一个按钮单独决定。`/model`、`/effort`
  网页输入框下已有。`!` 直跑 shell 没有替代，也不打算补。
- 文档里提到 TUI 的地方不少（`komo_bot.md` 44 处、`memory.md` 10 处等），删的时候要一并改，`PRODUCT.md` 的"一个世界，多个
  入口"也要改口。

CLI 自己还能再收一点，但与 TUI 无关，另算：`komo channel wechat login` 这个兼容别名；`komo session` 在有了 `komo task`
之后只留排查用的 `search` / `export` / `purge`（`list` 与 `delete` 并进 `komo task`，但 Agent 的系统提示和看门狗提示里
教的是 `komo session list`，要同步改）。

### 5.2 只剩网页与桌面端时，CLI 还剩什么（2026-11-10 提出）

CLI 子命令各有各的存在理由，"操作者不再坐在终端前"只消掉其中一种。按理由分三类：

| 类 | 命令 | 能不能去 |
|---|---|---|
| **启动与安装**：网页打开之前、或 Gateway 起不来时要用 | `komo gateway [--foreground\|status\|stop\|restart]`（launchd / systemd 与桌面端都调它）、`komo init`、`komo update`、`komo web`（浏览器的配对码从这来）、`komo doctor`、`komo config check`（配置错到 Gateway 起不来时只有它能说哪里错）、`komo auth codex\|mcp login`、`komo channel login`（微信二维码）、隐藏的 `__codemode-worker` | **去不掉**，除非桌面端接手（见下） |
| **Agent 的工具面**：Agent 在 `bash` 里跑，系统提示与工具文档里教的 | `komo memory add/search/confirm/forget`、`komo goal …`、`komo area …`、`komo skills list/inspect/enable/disable`、`komo cron …`、`komo mcp reconnect`、`komo session search/list`、`komo monitor list`、`komo run inspect`、`komo intervention list`（后三条是看门狗提示用的）、`komo gateway restart` | **去不掉**；可以从 `--help` 里藏起来 |
| **只给终端前的操作者**，网页已有对应 | `komo home`、`komo resume`；`komo session delete/purge`；`komo run cancel`；`komo intervention show/answer`；`komo memory list/show/classify/restore`、`komo memory index status/rebuild`；`komo config reload`；`komo channel list/probe` | **可以去** |
| 只给操作者，网页**没有**对应 | `komo session export`、`komo memory consolidate`、`komo memory sweep` | 去之前网页要补，或认定不再需要 |

所以直接能删的是第三类：顶层少 `home`、`resume` 两个，子命令少十来个。顶层 20 个里大多数还在，因为它们属于前两类。

要再往下收，是两笔单独的投入，都不是"删命令"：

- **桌面端接手启动与安装。** 现在桌面端只连接常驻的 Gateway、不持有它（`clients.md` §4），没在跑时调 `komo gateway` 拉起；
  首次配置、更新、Codex / MCP / 微信登录都还指向 CLI（网页 MCP 节对要登录的服务器写的就是 `komo auth mcp login <名字>`）。
  桌面端做完首次配置向导、登录流程与更新之后，这一类对桌面用户才不可见；二进制里仍要有 `gateway` 与 `__codemode-worker`，
  自托管在服务器上的用户也仍要 `init` / `gateway` / `web`。
- **把 Agent 的命令换成工具。** 不建议：命令经 `bash` 调用不占模型的工具定义，换成十几个工具每次请求都要带上它们的 schema，
  还要重做 `KOMO_SESSION` / `KOMO_RUN` 带来的"在 Run 里调用"的那套判断（记成未确认、引用户原话）。

**建议**：删第三类；第二类保留但 `hide = true`，不进 `komo --help`，并在 `--help` 里只留启动与安装那几条。操作者看到的
CLI 从 20 个顶层命令变成 8 个左右（`gateway` `init` `update` `web` `doctor` `config` `auth` `channel`），Agent 的用法一字不改。
Gateway 文案里指向被删命令的提示（渠道节的 `komo channel list|probe`、配置重载的提示等）改成指向网页。

### 5.3 照 Cabinet：只留"把服务启动起来"（2026-11-10 操作者提出，取代 §5.2 的建议）

Cabinet（`../cabinet`）没有 CLI：`pnpm start` 起一个进程，`deploy/install.sh` 注册 launchd，其余全在看板里——设置、路由规则、
飞书 OAuth（`/api/oauth/start`）都从网页发起。Agent 要记忆、要回查、要建定时任务，用的是三个工具（`memory`、`lookup`、
`schedule`，`server/agent/tools.ts`），不是命令。服务端场景下也确实没有人会登上去敲一串子命令。

§5.2 把 CLI 分成三类，认为前两类去不掉。照 Cabinet 的做法，这两类各有去处：

| §5.2 的类 | 去处 | 要做的事 |
|---|---|---|
| Agent 的工具面（`komo memory/goal/area/cron/session search …`） | **换成一个 `komo` 工具** | 在 Gateway 进程里执行，不经 shell：komo 可能在远程机器上，命令执行的地方不一定有二进制（§4.4）。并存一个版本后删掉这些子命令 |
| 启动与安装：`init` | 网页首次配置 | 没有配置时照样启动（现在无 key 也能启动），网页设置已能改模型、配置、环境变量；缺的是"一个 Agent 都没声明"时的引导 |
| `config check`、`doctor` | 网页设置的配置检查（已有 `GET /v1/config/check`） | 配置错到装不上时保留旧配置继续跑（热重载已如此）；**冷启动时配置就是坏的**要能起到只开设置页的降级状态 |
| `auth codex login`、`auth mcp login`、`channel login`（微信二维码） | 网页里发起 | 设备码与二维码显示在网页；MCP 的授权码回调现在听 `127.0.0.1` 随机端口，远程部署时要改走 Gateway 自己的回调地址 |
| `web`（配对码） | 启动日志里印一次性链接（同 DeepSeek Harness 的启动令牌，`clients.md` §7） | cookie 随 Gateway 重启失效这一点要么改成持久，要么留一条重新配对的命令 |
| `gateway status/stop/restart`、`update` | 交给 launchd / systemd / 容器与发布流程 | 桌面端自动更新；服务器上重新部署二进制 |
| 第三、四类（操作者用的各种 list / show / export） | 网页 | `session export`、`memory consolidate/sweep` 网页补入口或不要 |

收完之后的 CLI：`komo`（前台起服务，给 launchd / systemd / 容器用）、`komo --version`、隐藏的 `__codemode-worker`；重新配对
如果不做持久 cookie，再留一条 `komo web`。`crates/komo/src` 的 `commands.rs`、`matters.rs` 与 `komo-client` 的 `render/`、`api.rs`
大半可以删，`komo-client` 这个 crate 可能整个不需要。

这一条的来回（都在 2026-11-10）：先提四个按领域分的工具；操作者指出会变复杂，改为不加工具、命令藏出 `--help`；读了 OpenClaw 与
Hermes 之后操作者定加一个 `komo` 工具；操作者再指出 komo 可能在远程机器上，工具从"转给自家命令"改成在 Gateway 里执行。定稿见 §4.4。

**参照：OpenClaw 与 Hermes Agent 怎么做（2026-11-10 读本机 `../openclaw-latest`（当天的提交 `aa508b062`，浅克隆）、`../hermes-agent`）。** 两家在 Agent 这一侧都是工具，
没有让 Agent 在 shell 里调自家命令的：

| | 记忆 | 找回旧会话 | 定时 | 目标 / 派活 |
|---|---|---|---|---|
| Hermes（`toolsets.py`） | `memory`（`add` / `patch` / `remove`） | `session_search` | `cronjob_manage`（一个工具，`action` 取 create / list / update / pause / resume / remove / run / cancel） | `todo_list`、`delegate_task`、`kanban_*` |
| OpenClaw（`src/agents/tools/`、`docs/tools/index.md`） | `memory_search`、`memory_get`、`memory_store`、`memory_recall`、`memory_forget`（插件提供） | `sessions_search`、`sessions_history`、`sessions_list` | `automations`（别名 `cron`，一个工具带 `action`） | `get_goal` / `create_goal` / `update_goal`、`sessions_spawn`、`subagents` |

做法上的共同点：一个领域一个工具，用 `action` 参数分动作，不是一个动作一个工具；工具多了靠按需加载压成本（Hermes 的核心工具集
41 个，配 `tool_search` 延迟加载；OpenClaw 有 `tool_search` 与 Code Mode）。给人用的一侧两家都**没有**收到只剩启动：OpenClaw 的
`docs/cli/` 有 70 多个命令页（`onboard`、`doctor`、`channels`、`cron`、`memory`、`sessions` …），Hermes 也有 `hermes setup`、
`hermes dashboard` 等一整套。所以它们支持的是"Agent 的能力做成工具"这一半，不支持"CLI 只留启动"那一半，后者只有 Cabinet 是这样。
这不改变上面的建议（两家都不以精简为目标），但如果 D8 选备选，形态照它们：一个领域一个带 `action` 的工具。

另一处与 Cabinet 不同、保持本文原判断的：Cabinet 为任务建了新表 `tasks` 当父表（`docs/router-worker.md` §2.1），因为它有草稿、
审批、开发任务、问答四种各带状态机的产出要收拢；komo 的产出只有会话一种，所以 D1 仍建议只做投影。字段可以借它的：
`need`（等谁做什么）正是 §3.2"等你"缺的那一格，`thread`（归属键）对应群与话题会话的 peer。

不在这次范围：订阅直通（飞书话题已是一个话题一个会话，私聊按 `#短号` 确定性路由 10-08 已删，不恢复）、提前行动、
多 Agent 各自的主会话、渠道插件、记忆。

### 5.4 概念收拢：Memos 与领域（2026-11-11 操作者提出）

**Memos 移出核心概念（操作者定）。** 核对结果：Memos 在 komo 里没有专门的实现，接入方式就是一个普通 Skill，由 `bash` 跑它的脚本
（`komo_bot.md` §5.5）；代码里只有记忆证据的一个变体 `EvidenceRef::Memos`（`komo-kernel/src/types/memory.rs`），除测试外没有
任何地方构造它，只在几处 `match` 里被列出来。它在规格里却占了一节（§5.5）并出现在范围、记忆分工等十几处。要改的：

- `komo_bot.md` §5.5 整节删掉，§1 范围与别处的提及改成"用户自己的笔记工具经 Skill 接入，komo 不规定是哪一个"；
- `memory.md` §9.1 的分工表改成"用户主动保存的笔记不归 komo 管"，§9.2、§9.6 里与 Memos 原文核对的规则删掉；
- `EvidenceRef::Memos` 变体：`aux.db` 里有没有这种证据没查到（Gateway 在跑，库锁着），确认没有存量后删，有就只留解码。

**领域并进记忆的约定，只留目标（操作者 2026-11-11 认可，D10）。** 现状：目标与领域一张表 `matters`、`kind` 区分，两组命令。差别只有：

| | 目标 | 领域 |
|---|---|---|
| 状态 | 进行中 / 等待中 / 搁置 / 完成 / 放弃 | 在管 / 不再管 |
| 专属字段 | 下一步、在等什么、截止日期 | 标准（要维持的那句话） |

领域除了"标准"那一句话之外什么都没有，而"标准"和记忆里的约定是同一种东西——文档的例子"每周一前完成告警值班轮换"、库里唯一的
一条领域"每次发版都要带 SHA256SUMS，且 tag 等于 workspace 版本号"，都是"在某个场合照这条做"，正是带适用条件的约定；要定期做的
再配一条 Cron。实际使用也是这样：`komo area list --all` 只有这一条，而且已经是"不再管"。

做法：不再有领域这个概念，新的长期职责记成约定（周期性的加 Cron）；`komo` 工具不设 `area.*` 动作；"事项"这个统称随之不需要，
用户面前只叫"目标"。表与 `kind` 列不动，已有的那条领域保留可读、不迁移。要一并去掉的：`goals.md` 里领域的状态机与命令、
注入块里的"领域"行、记忆归属到领域这一支（记忆归属到目标的照旧）。

备选：留一个概念但不叫领域——没有终点的目标（`goal.add` 带"长期"标记，不能完成只能放弃）。少一组命令，但"标准"字段和
两种状态机还在，概念只是换了名字。

没查的：有多少条记忆归属到领域（同样因为库锁着）。有的话这些记忆的归属要清掉或改挂。

删"分叉"接口；T5 代操作者回复；真实模型与真机渠道上的验证。


每一步单独可用，前一步不依赖后一步。

- **T0 统计（不再是前提）。** 从 `durable.db` 读主会话的 Run：工具轮数与用时的分布、Run 期间有用户输入在排队的次数。只读。
  D3 已定，它只留作改之前的基线，想对比效果时再跑。
- **T1 任务投影与清单。** `GET /v1/tasks`、`komo task list/show`、网页侧栏换成主对话 + 任务清单、⌘K 改名。不改存储、
  不改 home 行为。完成标准：派出一个任务、直接开一个任务、让一个任务受阻，三者在清单里各在其位；归档后默认不显示。
- **T2 Router - Worker。** §4.11 的结构化判断，加 `komo` 工具（§4.4，给 Worker）。顺序：`komo` 工具 → 分发判断（输入拼装、四种去向、
  失败按 `new`）→ 进来的消息改走"先按 Thread 键路由，否则判断" → 飞书主线消息接进来（R6）→ 放开"由用户消息派出的任务可以改承诺"。
  完成标准：在微信里要求改一个文件，程序派出任务，结果原文回到微信；说"先别做了"，对应任务被停并交回已有的部分；问"手上有哪些事"，
  直接得到清单而没有模型回复；说"记住……"，派出的任务把它记下；判断调用报错时消息仍变成一个新任务。
  §4.14 的四条一并做：分发是引擎任务（受理后、派出前杀掉进程，重启后这条消息仍被派出且只派一次）；停下的任务名下监听一并停、
  晚到的事件不再起 Run；一个话题有两个候选任务时回到 Router 判断；主线消息在网页里看得见（新的事件映射与渲染路径）。
- **T2a 模型调用的容错（2026-11-12 已实现，分支 `feature/tolerance`，未提交）。** §4.10 的 P1–P3。完成标准：截断且带工具调用的回复之后任务继续、模型重发调用，连续截断到
  上限才失败；参数里有裸换行或没闭合的括号时工具照常执行；数字写成字符串时工具照常执行；三者各有测试，重启后回放的参数与首次一致。
- **T5 代操作者回复（§4.13，从 Cabinet 并入）。** 依赖 T2。顺序：飞书用户身份的授权与凭证 → 轮询入站（私聊、群里 @操作者）→ 这条路的
  Router 判断与只读 Worker → 草稿卡片与三个动作 → 以操作者身份发出的唯一入口 → 四种作废。完成标准：群里有人 @操作者 提问，操作者私聊收到
  一张草稿卡片；点"发"后群里出现一条以操作者本人身份发的回复；改字再发，发出的是改后的字；操作者先自己回了，卡片变成"已作废"且
  没有任何东西发出；群里有人贴 MR 让操作者看，Worker 能拉代码、跑单测，产物都在独立目录里；它调用对外工具时停下来等批。
- **T3 精简会话面。** §5 标"删"的各项，连同对应的路由、TUI 命令、测试与文档段落；`handoff.md` 归档。D7 认可的话 TUI 在这一步

  `cargo test --workspace` 通过，`session-tree.md` §4 里对应的测试随功能一起删掉或改写，没有悬空的文档引用。

  旧子命令并存一个版本；再把登录、首次配置、配对搬进网页；最后删命令与 `komo-client`。完成标准：一台只装了二进制的机器上，起服务、打开启动日志里的
  链接、在网页里配好模型与一个渠道、让 Agent 记一条记忆和一个目标，全程不敲第二条命令。
- **T4 归属。** 任务带上目标的键（§4.7），目标详情页列出带该键的任务。
