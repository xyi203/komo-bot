# 差距与路线：朝 Muse 那种形态走

> 状态：路线草案（2026-10-28）。§4 里标「决定」的已认可，其余未认可、未实现。与 `docs/komo_bot.md` 冲突处以设计文档为准；这里只列差距、先后与要拍板的决策，各项认可后再写进对应的规格（记忆进 `docs/memory.md`，其余进 `docs/komo_bot.md` 或单独的设计文档）。

## 1. 目标形态

参照 Meta 2026-09 发布的个人 agent Muse（muse.ai）。公开资料以媒体报道为主，**没有讲记忆的存储与检索机制**，下面只取报道里讲得出机制的部分：

- **一条长期对话**，复杂项目开旁路对话；能接着上次继续。
- **记忆可看、可改**：用户能查看和编辑记忆文件；在对话里说一句就能让它忘掉某件事。
- **主动**：不等提问就发消息；定时任务与事件驱动任务（报道里的例子：盯着学校邮件与学区网站，把日期写进日历、提醒一次选拔赛）；自己判断新结果值不值得通知；主动程度可以调低、调高或关闭；有一个 Goals 页。
- **后台执行**：每个用户一台云端 VM（文件系统、终端、浏览器），关掉 App 也在跑；有变化或需要批准时才回来找人。
- **对外动作要批准**：发邮件、付款前弹出接受 / 拒绝卡片；另一个 agent（Sentinel）把关所有联网请求。
- **连接器按服务授权**：选哪些服务、给什么级别（邮件只读或可发送），随时撤销；有完整的活动日志，列出做过的和打算做的事。
- **渠道**：App、网页、WhatsApp。

不照搬的：报道称它会照着"只提过一次"的话做事，没有给出机制；komo 坚持只有用户表达了长期意图才算约定（`docs/memory.md` §9.2），一次性的话只当线索。

### 组织原则：借 PARA

PARA（Tiago Forte 的笔记法）把个人信息分成项目（Projects）、领域（Areas）、资料（Resources）、归档（Archives）。对个人 agent 有用的不是四个文件夹，而是两条原则：

1. **按"现在要不要用"组织，不按主题。** 决定一条信息该不该出现在上下文里的，是它和手上正在做的事有没有关系，而不是它讲的是什么话题。
2. **事情会结束，相关的东西跟着归档。** 项目办完，为它记下的材料一起退出视野，但还找得到。

| PARA | 含义 | 在 komo 里 | 怎么出现在上下文里 |
|---|---|---|---|
| 项目 | 有目标、会结束的事 | **目标**（P1）。命名上不叫"项目"：记忆作用域里已有 `project:<id>`，指代码仓库 / 工作目录 | 进行中的目标每段都带一份清单 |
| 领域 | 没有终点、要维持标准的职责：告警值班、家里的设备、孩子学校的通知 | **领域**（P1）。今天的约定、告警轮换 cron、设备 monitor 其实都属于某个领域，但没有挂在一起 | 在管的领域每段都带一份清单；它的约定每段都带；细节过门槛才带 |
| 资料 | 感兴趣、以后可能用上的参考 | 不挂在任何目标或领域下的线索；Memos、skills | 不主动推，Agent 需要时自己 `komo memory search` |
| 归档 | 前三类里不再活跃的 | 已遗忘、被取代、过期的记忆；结案目标下的线索；不再管的领域 | 从不注入，只在显式查询时出现 |

两个现成的证据：

- 2026-10-28 清理掉的 12 条记忆，多数是"已经做完的事"留下的要求（TUI 取消提示、规范变了才附……），事情做完了却一直被注入。记忆现在只有作用域，不知道自己属于哪件事，没法跟着结束。
- 同一天的真实实例复核里，问 Rust 问题却带进了 devops-mcp 的 `issueKey`（P0 复核记录）。按 PARA，它是不属于任何进行中事项的资料，本来就不该主动推。

不借的：让用户自己维护分类（分类由模型提议、事件驱动，用户只确认转换）；文件夹层级（只取"要不要用"与"生命周期"两个维度）。

## 2. 差距

| 能力 | Muse | komo 现状 | 差距 |
|---|---|---|---|
| 长期对话 | 一条主对话 + 旁路对话 | 渠道会话、主会话、`task` / fork 子会话（`docs/background-tasks.md`、§8.11） | 小 |
| 跨任务记住偏好 | 记忆贯穿对话 | 约定 / 线索分开、门槛、每个 Run 召回一次（`docs/memory.md` §9.2–§9.4，已实现）；约定不过门槛与 Agent 主动查已实现并安装 | 小 |
| 记忆可看可改 | 记忆文件，可编辑；对话里说忘就忘 | 只有 `komo memory list/show/search/forget/classify` 命令；Agent 能在 Run 里替用户 forget，确认与分类只能操作者做（§9.6） | 中：没有面向用户的视图 |
| 目标与领域 | Goals 页；"注意到和你目标相关的信息" | 没有"目标"和"领域"这两个对象；记忆的种类（偏好 / 事实 / 经验）和使用方式（约定 / 线索）都表达不了"正在做、会结束的事"和"长期在管的事" | **大** |
| 记忆跟着事情结束 | 未公开 | 记忆只有作用域，不知道属于哪件事；做完的事留下的要求一直被注入，只能人工 forget | 中 |
| 主动触发 | 定时 + 事件；自己判断要不要通知 | Cron（时间，`notify` 三档只按成败过滤）、monitor（事件，交回会话后由模型决定转不转告）、投递与 home chat（§11.4） | 中：触发器齐了，缺"为谁、为什么盯"和"值不值得说" |
| 主动程度控制 | 降低 / 提高 / 关闭 | 没有全局开关；只能逐个 cron 的 `notify` | 中 |
| 后台执行 | 隔离 VM | Task 引擎、后台任务、可恢复（§8） | 小（隔离另算，见下） |
| 对外动作批准 | 发邮件、付款前审批卡；联网由 Sentinel 把关 | 2026-10-11 删掉 Policy 与审批（§7）；需要人的只剩 faulted 任务的 intervention | **需要拍板**，见 §4.1 |
| 执行隔离 | 每用户一台 VM | 直接跑在操作者机器上；bash 有账号全部权限，唯一的执行环境边界是 codemode（§7.3） | 大，但不急 |
| 连接器 | 邮件、日历、购物、健康……按服务给访问级别 | MCP 服务器、skills、飞书 / Telegram / 微信；MCP 没有访问级别 | 中 |
| 活动日志 | 做过的和打算做的 | durable entry 是完整审计；`komo session export`、run 详情、遥测；没有面向用户的"它最近替我做了什么" | 中 |

## 3. 路线

按依赖排，前一阶段是后一阶段的地基。

- [x] 实现 `docs/memory.md` §9.4「约定不过门槛，Agent 主动查」：约定每段全量带上；`komo memory search` 按会话作用域、结果不被提取当证据（2026-10-28，已实现）。

真实实例复核（2026-10-28，会话 `01a182f9-d3c0-7d49-89c7-d358b81935a5`）：第一句问与发布无关的 Rust 问题，召回块照样带上两条约定（不过门槛）；第二句「帮我把 owl 服务上线一下……Platform 你会选什么」，召回记录 `uses` 为空（同段不重复带），回答直接选 saas、没有追问。同一会话第一句还带进一条无关线索（devops-mcp 的 `issueKey`），`komo run inspect` 看不到它的两臂分数，门槛是否要重新校准待查。private Agent 那一条只有自动化测试（`tests/memory/session_search.rs`），没在真实实例里复核。

### P1 目标与领域（借 PARA，见 §1「组织原则」）

主动性要有"为谁、为什么"，记忆要有"属于哪件事"。komo 现在两样都缺。

- **两种事项，一张表**（`aux.db`，与 cron 同类），`kind = goal | area`：
  - **目标**：有目标、会结束（"这周把 owl 的发布观察做完""给孩子报名选拔赛"）。生命周期：进行中 / 完成 / 放弃 / 过期，可带截止时间。命令 `komo goal add/list/show/done/drop`。
  - **领域**：没有终点、要维持标准的职责（"告警值班轮换""家里的热水器和空调""孩子学校的通知"）。生命周期：在管 / 不再管。命令 `komo area add/list/show/retire`。
  - 都带用户原话证据，都能挂若干触发器（cron、monitor），带自己的通知偏好。主动提醒多半来自领域（盯着标准有没有被打破）和目标（截止前提醒）。
  - Agent 在 Run 里用 bash 代记，证据规则同 `memory add`（§9.3）；不是记忆的第三种使用方式：记忆是"知道什么"，目标与领域是"在做什么、在管什么"。
- **记忆归属**：记忆条目加一个可选的归属（某个目标或领域的 id），与作用域并存、互不替代。提取时把进行中的目标与在管的领域列给模型，由它建议归属；`memory add --for <id>`；`classify` 也能改归属。改归属算内容语义变化，升 revision（同改 application，§9.2）。
- **结案归档**：
  - 目标完成或放弃、领域不再管时，挂在它下面的**线索**转为新状态 `archived`：不注入，`search` 默认不返回，`--include-archived` 能查到；目标重开时恢复。
  - 挂在它下面的**约定**不自动归档：约定是长期意图，不能悄悄消失。结案时列出来问一次——提升到某个领域或个人，还是遗忘（操作者动作，同 classify）。没答之前照常注入。
- **注入按"现在要不要用"分层**（改 `docs/memory.md` §9.4 的现状）：
  1. 进行中的目标与在管的领域：一行一个的清单，每段带一次，机制同约定（全量、按 `id@revision` 去重、失效即改写），单独预算。
  2. 约定：每段全量（P0 已实现）。
  3. 挂在进行中目标 / 在管领域下的线索：过门槛才带（现状）。
  4. 其余线索（资料）：不主动推，只能 `komo memory search`。这一条改变现有行为，先加开关 `[memory.retrieval] push_unattached`，默认 `true` 保持现状；存量挂好归属、观察一段漏召回之后再改默认。
  5. 归档：只在显式查询时出现。
- **提取**：提示词识别"开始做某事 / 开始管某事 / 某事办完了 / 不管了"，产出新建与结案建议，进候选，用户或 Agent 确认后生效；记忆的归属建议同理。不让用户手工归档。
- **存量**：现有记忆归属为空，行为不变。出一份归属建议清单，操作者审过后批量挂上（同 2026-10-28 那次 classify）。
- 待定：目标与领域是否按渠道 / 会话归属；过期策略；领域与记忆作用域 `environment:<id>` 的关系（"家里的设备"这类领域可能就对应一个 environment 作用域，要不要合一）。

完成标准：
- 在飞书里说"帮我盯着孩子学校的通知"，建一个领域并挂上 monitor；说"这周把 owl 发布观察做完"，建一个目标。
- 做这件事时提取出的线索挂到这个目标下。
- 说"owl 那件事搞定了"：目标结案，它下面的线索不再注入、仍能 search 到；挂着的约定被问一次。
- 任何会话问"我在管哪些事、在做哪些事"都答得出来。
- `push_unattached = false` 时，问无关问题不再带进不属于任何进行中事项的线索。

### P2 主动：通知判断与主动程度

- **通知判断**：目标或领域的触发器跑完，不再按成败直接投递，而是由这次 Run 交回"说 / 不说 / 攒到摘要里"三选一并写理由；判断时能看到这件事本身（目标的截止、领域的标准）。判断记进 Run，便于事后看漏报误报。`notify` 三档保留给没挂事项的 cron。
- **主动程度**：全局 `[proactive] level = off | low | normal | high`，加免打扰时段和每日条数上限；`off` 时目标与领域照常记录，触发器不跑。聊天里一句"少打扰我"改的就是它（操作者动作，同 confirm）。
- **摘要**：`low` 档把"可以不立刻说"的攒成每天一条。
- 依赖 P1；复用 Cron、monitor、Notifier，不新增执行通道。

完成标准：一个挂了 monitor 的领域一周内的投递条数、被忽略条数可以统计；调成 `off` 后零投递。

### P3 对外动作确认（已拍板，见 §4.1）

只覆盖"代表用户对外说话或花钱"的那一小类，不恢复 Policy。

### P4 可见：记忆、目标、领域与活动

- TUI 与聊天里的 `/memory`、`/goals`、`/areas`：一条一行，带使用方式、条件、来源、归属；能在这里 forget、结案、确认归档时约定的去向。记忆按归属分组看（某个目标或领域下记了什么）。
- 活动页："最近替你做了什么、接下来打算做什么"，读 durable entry 与目标、领域的触发器计划，不另建账本。
- 记忆的可编辑视图只做**投影**（像 hindsight 把知识页投成 markdown），改动经命令回到 `aux.db`；不让文件成为第二权威（§8.2）。

### P5 连接器与隔离（远期）

- 日历、邮件等个人服务经 MCP 接入，按服务配访问级别（只读 / 可写），在能力面（`AgentSurface`）上体现，而不是在命令文本上判断。
- 无人值守的主动 Run 放进执行环境里跑（§7.3 说的"把 bash 放进同类执行环境"），联网出口单独把关。

## 4. 要拍板的决策

### 4.1 对外动作要不要确认

2026-10-11 删掉审批的依据是：操作者一直跑 auto，152 次审批 148 次批准、等待中位 3.2 秒，审批没有在判断什么（`docs/komo_bot.md` §7）。那些审批都发生在**操作者自己发起、自己在看**的 Run 里。主动形态改变了这个前提：P2 之后会有大量没人在看的 Run，它们可能替用户发消息给别人、改日历、下单。

**决定（2026-10-28，操作者认可）**：不恢复规则表，只给"由触发器发起、且这次动作是对外发消息 / 付款 / 删除外部数据"的调用加一张确认卡，走现有 intervention 投递（§7.5、§11.4）；用户发起的 Run 维持现状。哪些工具算"对外"由工具（或 MCP 服务器配置）声明，不解析命令文本。

### 4.2 目标与领域单独成对象，还是记忆的一种

建议单独成对象，记忆挂到它们下面（P1 的理由）；代价是多一张表、两组命令、记忆多一个归属字段和一个 `archived` 状态。

### 4.3 主动消息走哪个渠道

默认 home chat；目标或领域可以指定渠道会话。微信不能在进程重启后主动推送（§11.4），主动消息优先飞书。

### 4.4 手机端：先用飞书，不做原生 App

**决定（2026-10-28，操作者认可）**：手机端先用飞书，不做原生 App。

- Muse 的 App 主要提供一条长期对话、主动推送和审批卡片，komo 在飞书里都有对应：渠道会话、投递到 home chat、确认卡走 intervention 投递（§4.1）。
- 原生 App 最大的成本是把 Gateway 暴露到本机之外：现在只监听 `127.0.0.1`，鉴权按本机单操作者设计，手机直连要走 Tailscale 或内网穿透并重做鉴权。飞书由它的服务器中转，komo 不对外开端口。另外还要维护 iOS / Android 客户端、上架或 TestFlight、推送证书。
- 飞书不够的地方：成页地看记忆 / 目标 / 领域 / 活动（P4）先做 `/memory`、`/goals`、`/areas` 这类聊天命令，真要页面时由 Gateway 出只读网页、手机浏览器打开；主动程度、免打扰这类设置在聊天里一句话改（操作者动作）。
- 重新考虑的时机：要接手机上的个人数据（位置、健康、相册，P5 连接器），或飞书的推送频率、卡片交互明显不够用。
